# Knowledge Change: exact baseline and identity

Read the backend baseline manifest, current lifecycle and exact source revisions. Inspect each target's current and inherited profiles, bindings, validity/freshness and dependencies. Identify which accepted state the proposed operation changes. Missing or inaccessible evidence stays missing; never invent a source, revision or authority reference.

For create, compare the proposed meaning with the explicitly available existing identities. Match scope, epistemic status, conditions and exceptions, not just title. An exact duplicate can support no_change; a similar title or vector score cannot settle identity. An empty exact-match result does not prove that the whole company corpus contains no equivalent knowledge. Record the considered candidates and limits.

For revise/revalidate/retract, pin the unit and accepted revision. For supersede, inspect predecessor and successor and the exact bindings being replaced; preserve unaffected scope. The successor must already be eligible or be created by a related operation in this Change. Do not rewrite historical consumer pins. For erase, identify all target revisions and known source/copy ownership without expanding the deletion scope.

Return a baseline assessment tied to the supplied manifest/generation: target and source pins, identity match decision and rationale, current states, dependencies and explicit gaps/conflicts. Put your unresolved semantic findings in `assessment_conflicts` and missing context in `assessment_gaps`. The backend recomputes `conflicts` and `missing_context` from its current checks together with those authored findings; do not overwrite computed diagnostics or assume that a refresh resolves a semantic issue. Persist an honest waiting assessment when anything remains unresolved. Close authored findings only through a new substantive reconciled assessment. If a head or applicable norm changes later, return here and reconsider the difference; changing expected_revision alone is not reconciliation.

If the assigned expected target changed, read the current exact unit and compare the difference before submitting `knowledge.change_record_input` with a typed `basis_amendment`. Name the prior expected revision/lifecycle and the full replacement guard of the same unit. If newly obtained evidence replaces the source set, supply the complete replacement source list explicitly. The backend checks current authority, native target truth and exact sources, preserves the previous basis, and returns this run to KC02 with downstream outputs and seal invalidated. Inspect the accepted amendment and source-set revision, then perform qualification, evidence checks and reconciliation again. Never submit an unchanged old seal or claim old check receipts cover the new basis. Changing the operation, target identity, intent or authority scope requires a separately authorized Change; a committed Change cannot be amended.

Source: design §5, §7.9–7.11, §7.13; V1 existing-match, context and source-authority methods.
