# Knowledge Change: truthful result and handoff

For an all-Erase request whose exact targets were already fully suppressed, the backend may deliver KC12 directly with an `erased_no_change_proof`. Read that opaque proof and the requested completion flags. Do not reconstruct deleted source text, invent an RDF digest or claim KC01–08 were executed. The backend rechecks the existing ledger, residual and any required export before accepting no_change; this path has no new publisher receipt or erasure sequence. Submit only the bounded terminal outcome. Free-form body and summary are not retained on the erased path, and a managed Promotion Result/planning input remains redacted.

Compare the actual result with the saved intent and completion contract. Read the backend publisher receipt and current effects state separately. Report exact operation/unit/revision/event references, canonical status, current delivery eligibility, impact/follow-ups, search capability and erasure/backup disposition. A historical receipt is immutable; current effects may have changed since it was issued.

Only the backend commit receipt proves canonical publication. An agent string such as promoted=true, a prepared RDF draft, a source file or a completed producer phase does not. A producer may correctly say durable_write_performed=false while linking a successful backend publisher receipt: the producer did not own the canonical write.

Achieved means the requested outcome and all required effects are met. Partial names the accomplished part and exact remainder. Not-achieved preserves the original objective and required input/action. Rejected is not successful publication. No_change is successful only when the guarded existing result satisfies intent. A freshness event is applied work, not no_change. A dependency handoff is not completion unless the work's contract was explicitly changed.

If an ordinary no-change or rejected review needs correction before this terminal handoff is accepted, and no canonical publication has occurred, record the exact new input and revisit the appropriate KC02–KC07 phase on the same run. A drifted no-change basis must be requalified, not repeatedly submitted as an achieved result. The backend invalidates the old review, clears its terminal branch and changes delivery to phasewise. This continuation does not apply to a completed run, an already-published Change or an erased opaque run; those retain their existing follow-up or suppression boundaries.

For erase, distinguish immediate visibility closure, actual purge of owned live content, backup/retention status and uncontrolled copies. Never label full erase complete while required copies remain. If search was required, unavailable indexing cannot be relabelled not-applicable after failure. If a nonblocking effect was explicitly permitted to continue, name its stable identity, state and owner without claiming it finished.

After payload erasure, use the backend's explicit opaque continuation instead of rereading removed intent, drafts, source hashes or sealed command bytes. Do not repeat the erased title, source or claim in a new handoff. The backend verifies the terminal outcome from opaque operation and effect identities and retains only that terminal projection with a generic summary; submitted semantic body/request copies and their raw hashes are not retained. This erasure branch does not turn an empty or redacted output into valid publication evidence. Surviving independently owned knowledge keeps its canonical identity and remains separately readable within current access.

For a Promotion Slice, let the backend assemble the managed Slice Result from this Change and its receipts; do not run a second copy of the lifecycle. An achieved applied/no-change outcome produces a completed Slice Result. A terminal rejected or partial/not-achieved outcome produces a blocked Slice Result with the exact remaining objective, never a completed Slice. Both terminal results feed the existing Scope replanning boundary once; waiting checkpoints remain on the same Knowledge cursor and produce no terminal Result. A finished rejected proposal or a post-commit semantic correction needs separately planned follow-up work, not a hidden restart of the old run. Recommend only a concrete next needed task. Do not create skills, start research, execute a runbook, repair a server or send a message as an implicit final step.

Source: design §7.10 KC-12, §7.15, §13.1–13.7; V1 promotion-result/final-handoff boundaries.
