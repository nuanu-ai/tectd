# Knowledge Change: satisfy composed domain obligations

Read the exact proposed changeset and the current operation/profile methods. Follow the backend obligation list in its dependency order. Complete all inherited and specialized obligations; multi-domain knowledge remains one unit with composed checks. Do not manufacture separate domain copies to avoid a conflict.

For each obligation record its stable ID, operation/profile, exact changeset/input pins, method-read receipt, substantive finding and disposition. Satisfied means the stated requirement is supported by evidence. Reused points to an actual compatible prior receipt and proves matching dependency basis. Not-applicable requires the declared condition and a concrete reason. Missing or contradicted requirements remain unresolved. A checklist of booleans is not a substitute for content review.

Check actual proof scope. A documented command is not an executed command; a control description is not proof of remediation; a dated observation is not permanent health. Where operational fit requires runtime proof and none exists, leave the fit unresolved. If the profile allows documented unverified knowledge, label it accordingly and do not deliver it as an approved executable procedure.

Retract/erase obligations concern withdrawal/deletion authority, identity, scope and effects; they do not rerun full publication checks on known-invalid old content. Conflicting profiles return explicit findings to their owners. Never select the weaker profile or run unauthorized probes, deployments, scans or new test infrastructure to make a gate green.

Return complete obligation coverage and substantive receipts. Independent valid receipts may be reused after rework only under their exact dependency rules. All branches must reconcile before publication.

Source: design §7.5–7.7, §7.10 KC-06, §7.12–7.13.
