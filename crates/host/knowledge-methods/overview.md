# Knowledge Change lifecycle

One Knowledge Change owns one ordered run, whether opened directly in a workspace or through a Promotion Slice. Its phases are intake, exact baseline, branch qualification, evidence qualification, proposed change, domain checks, impact plan, review/reconciliation, publication gate, canonical commit, effect settlement and result handoff. Workspace entry and Promotion use the same methods and publisher. A producer's research or procedure-capture run retains its own work and hands off exact outputs; it does not create a second Knowledge cursor.

Compose General with every applicable domain profile for each operation: create, revise, revalidate, supersede, retract or erase. Read the exact delivered methods at their required phases and submit substantive outputs bound to current inputs, source versions and prior outputs. Whole delivery exposes the ordered contract; it does not execute phases in parallel or waive their dependencies. Phasewise delivery exposes the current work. Missing context, conflicting evidence or a material input change requires an explicit revisit and invalidates dependent receipts; changed method versions require new reads.

Use the phase-tagged schema advertised by help for `knowledge.change_phase_complete` when constructing semantic data. It defines the exact fields, typed profile sections, allowed variants and bounds. The delivered methods explain how to establish the meaning and evidence for those fields; structural validity alone does not establish their truth. Keep backend-issued pins from the current action and leave explicitly computed fields for the backend. Do not infer field names from prose or treat an unavailable required field as permission to omit the underlying obligation.

The agent proposes and reviews meaning. The backend resolves identity and authority, compiles obligations, validates current guards, seals one command and applies the canonical transaction. KC-09, KC-10 and KC-11 are actual backend operations; do not submit invented semantic outputs claiming they happened. Retries reuse exact idempotency keys only for the same request and remain subject to current access. After commit, correct meaning through a new Change and retry only outstanding effects.

Canonical acceptance, exact delivery, consumer impact, search readiness, erasure and the user's outcome are distinct. Vector/search work is not configured in this version. Erasure preserves an explicit boundary between owned live-data removal, restore suppression and physical backup/storage disposal. Required unavailable capabilities block the relevant completion contract before publication. A no-change result identifies an already eligible exact result and rechecks its current guards. A rejected proposal does not achieve a publication request.
