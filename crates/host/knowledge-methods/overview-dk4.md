# Knowledge Change lifecycle

One Knowledge Change owns one ordered run, whether opened directly in a workspace or through a Promotion Slice. Its phases are intake, exact baseline, branch qualification, evidence qualification, proposed change, domain checks, impact plan, review/reconciliation, publication gate, canonical commit, effect settlement and result handoff. Workspace entry and Promotion use the same methods and publisher. A producer's research or procedure-capture run retains its own work and hands off exact outputs; it does not create a second Knowledge cursor.

Compose General with every applicable domain profile for each operation: create, revise, revalidate, supersede, retract or erase. Read the exact delivered methods at their required phases and submit substantive outputs bound to current inputs, source versions and prior outputs. Whole delivery exposes the ordered contract; it does not execute phases in parallel or waive their dependencies. Phasewise delivery exposes the current work. Missing context, conflicting evidence or a material input change requires an explicit revisit and invalidates dependent receipts; changed method versions require new reads.

Use the phase-tagged schema advertised by help for `knowledge.change_phase_complete` when constructing semantic data. It defines the exact fields, typed profile sections, allowed variants and bounds. The delivered methods explain how to establish the meaning and evidence for those fields; structural validity alone does not establish their truth. Keep backend-issued pins from the current action and leave explicitly computed fields for the backend. Do not infer field names from prose or treat an unavailable required field as permission to omit the underlying obligation.

The agent proposes and reviews meaning. The backend resolves identity and authority, compiles obligations, validates current guards, seals one command and applies the canonical transaction. KC-09, KC-10 and KC-11 are actual backend operations; do not submit invented semantic outputs claiming they happened. Retries reuse exact idempotency keys only for the same request and remain subject to current access. After commit, correct meaning through a new Change and retry only outstanding effects.

Canonical acceptance, exact delivery, consumer impact, search readiness, erasure and the user's outcome are distinct. Canonical publication atomically updates the lexical projection and invalidates obsolete search work. With optional vector capability enabled, the backend queues title embeddings; canonical commit can succeed while SearchRequired remains Pending. Follow the returned effect-settlement action and current state without republishing the Change, fabricating Ready or entering an unbounded polling loop. With vector capability explicitly disabled, SearchRequired requires current lexical state. With vector capability enabled but its provider unavailable, the required effect remains Pending. Determine readiness from current backend effects even when a producer's pinned instructions describe an older runtime. A title-only vector is a derived resource field; similarity supplies candidates and does not establish applicability or authority. Exact context delivery and graph-only search do not invoke the embedding model.

For Program formation, Scope shaping and Slice-candidate planning, a unit may carry reviewed `planning_briefs` in its same immutable content revision. Author the useful consequence at the requested level: business intent and strategic constraints for Program, boundaries and dependencies for Scope, vertical outcomes and proof or pipeline-choice constraints for Slice candidates. Preserve material conditions, exceptions and exact source identity. The backend uses explicit context, selectors, bindings and versioned needs to capture these briefs; it does not create an unreviewed summary from the full unit at read time. A unit without a suitable brief remains valid knowledge but is not automatically injected at a higher level. A brief cannot weaken the requirement of its applicable binding. An unresolved required need stays visible, including unknown applicability context. Empty DK allows a first Program and plan.

Maintenance observes exact reasons and evidence bases, deduplicates tasks and recovers bounded mechanical work. It does not manufacture fresh meaning. A linked task resumes this same Knowledge Change lifecycle and must obtain relevant new evidence for semantic revalidation. An existing source is baseline unless a genuinely new verified source version or observation establishes the current claim. Source changes, dependency changes and failed application can require review before a calendar date is due. Read the delivered maintenance method and exact task basis. An unrelated successful Change or a completion string does not settle that task; the backend checks its actual publisher outcome and covered basis. Later uncovered signals remain unresolved.

Erasure distinguishes owned live-data removal, restore suppression and physical backup/storage disposal. Its search closure requires actual removal of lexical copies, vectors and pending or leased jobs. Its delivery closure also covers owned knowledge copies and exact consumed lineage in Program/Scope drafts, Slice-candidate plans, manifests and command receipts. Preserve independently supplied user input; when an inseparable derived carrier must be removed, record the reviewed collateral and an honest erased/gap state. A late result cannot restore an erased resource; managed restore invalidates old leases before allowing new work. Unsupported completion requirements retain their explicit refusal. A no-change result identifies an already eligible exact result and rechecks its current guards. A rejected proposal does not achieve a publication request. Publishing knowledge does not activate an optional dependency, execute a runbook, grant operational permission or start new research.
